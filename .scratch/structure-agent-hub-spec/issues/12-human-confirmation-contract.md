## Question

在 [三类 Agent 与 MCP 如何支持逐次人工确认](11-confirmation-capability-evidence.md) 的取证之后，与工程师共同确定逐次确认如何落实为可检查的保障与验收，包括：

- 是否需要技术性闸门（在执行前由机制拦截），还是以流程与文档约束为主；二者各自承担什么。
- 责任归属落在哪里：Skill、MCP、Agent 客户端配置或使用方约定。
- 确认与实际操作、参数、目标对象及版本修订之间如何对应；目标在确认后发生变化时如何处理。
- 能力限制、绕过客户端的直接调用、部分执行或失败时如何处置与报告。
- 这些保障如何被验收，以及由谁在什么条件下判定成立。

须保留 [首批结构工程场景与 Hub 成功标准是什么](01-first-workflows.md#answer) 已经要求的人工确认：每项独立模型改动、每次分析运行前均须工程师逐次明确确认，覆盖已有文件另行确认，YJK 一次完整预览后的创建可只确认一次；确认前须展示目标、拟改内容（必要时含原值与新值）、已知影响与分析设置，未知影响如实标注；工程有未保存内容时，须先由工程师选择「使用当前会话状态另存副本」或「使用已保存文件」，选择前不覆盖原文件。本票不预设技术设计，也不修改上述已定要求；如何与 [仓库如何组织，Skill 与 MCP 如何分工](06-repository-skill-boundary.md) 的职责划分衔接，由用户判断。

参考票：[首批结构工程场景与 Hub 成功标准是什么](01-first-workflows.md)、[仓库如何组织，Skill 与 MCP 如何分工](06-repository-skill-boundary.md)、[三类 Agent 与 MCP 如何支持逐次人工确认](11-confirmation-capability-evidence.md)。

## Answer

用户于 2026-11-06 确认按推荐答案记录（「按推荐答案」）。本票是 planning-only 的 HITL 决策票：以下为 SPEC 的确认保障与验收基线，不是已实现的机制，也不是运行时验证结果。本轮未开发 MCP/Skill、未写 SPEC 正文、未部署客户端、未执行任何调用。

### 1. 保障形态：服务器侧技术闸门为主，客户端配置为纵深，流程文档约束人侧

- **技术闸门（机制层，执行前拦截）**：
  - 主闸门在 MCP 服务器侧：每个 mutating 操作（模型改动、分析运行、覆盖已有文件）在执行前必须持有有效的**操作单**（见 §3）；无有效操作单即拒绝执行并返回结构化错误，说明如何取得确认。该闸门对**所有调用路径**生效——直连 `tools/call`、非交互会话、任何客户端——因为校验在服务器内完成，不依赖客户端提示。
  - 闸门能证明什么、不能证明什么：它能证明「每次 mutating 执行都对应一份已记录、参数完整的操作单，且实际执行与操作单一致」，并阻止无操作单的静默改动。它**不能**证明提交操作单 ID 的一定是人：若调用方本身是恶意的，它可以自行申请操作单再自行回传 ID。因此「人已批准」这一层由流程约束（禁止直连、确认前审阅）与客户端纵深共同承担，不得宣称服务器闸门单独提供人类批准证明。
  - 客户端配置为纵深：部署契约（[一键部署应承诺什么行为与验收结果](08-deployment-contract.md)）要求把 mutating 工具配置为逐次 `ask`；Claude Code 可用 `_meta["anthropic/requiresUserInteraction"]` 强制每次必答；pi 需扩展 `tool_call` 门；OpenCode 需 `ask` 规则并明确 `always` 的降级风险。客户端层只提高可见性与拦截率，不作为唯一保障，也不作为「人已批准」的证明。
- **流程文档约束人侧**：禁止绕过客户端直连服务器执行 mutating 操作；非交互/无人值守会话不得执行需确认的操作；确认前须审阅操作单内容。
- 依据：[三类 Agent 与 MCP 如何支持逐次人工确认](11-confirmation-capability-evidence.md#answer) 证明客户端层单独不可靠（pi 无内建权限系统、OpenCode `always` 可持久降级、Claude Code 非交互退化、直连绕过全部客户端机制），且协议层无审批原语。

### 2. 责任归属

- **MCP 服务器**：生成操作单、校验确认、执行、记录结果与部分失败；组织并展示票 01 要求的确认内容（目标、拟改内容含原值/新值、已知影响、分析设置、未知标注）；在 `tools/list` 中为 mutating 工具声明 `_meta["anthropic/requiresUserInteraction"]`（Claude Code 专属，其他客户端不识别）。
- **客户端配置**：部署契约（[一键部署应承诺什么行为与验收结果](08-deployment-contract.md)）落实 §1 的纵深要求（逐次 `ask`、`requiresUserInteraction`、pi 扩展门、OpenCode 规则与 `always` 降级风险说明）。
- **Skill**：只负责编排与如实呈现，不承担安全闸门；MCP 不得以 Hub Skill 或特定客户端为运行依赖（[仓库如何组织，Skill 与 MCP 如何分工](06-repository-skill-boundary.md#answer)）。
- **使用方约定**：禁止直连、非交互限制、确认前审阅、未保存内容的选择流程（[首批结构工程场景与 Hub 成功标准是什么](01-first-workflows.md#answer)）。

### 3. 确认与操作/参数/目标/版本的对应：操作单

- **操作单（operation manifest）** 由 MCP 为每个待确认操作生成，至少含：唯一 ID；目标对象标识（软件内对象 ID / 文件路径 + 版本标识，如文件哈希或工程保存版本）；操作类型；参数（原值/新值）；影响说明（未知如实标注）；分析设置（分析运行）；生成时间。
- 工程师确认时回传该 ID；执行时服务器校验：ID 一次性有效、未被使用、**实际执行参数与操作单记录逐项一致**（不一致即拒绝）、目标当前状态与操作单一致（如文件哈希/修改时间、对象句柄或版本标识）。
- **目标在确认后变化**：操作单作废，拒绝执行，重新生成操作单并重新确认，如实报告变化内容。
- 确认只授权该操作单描述的那一次操作，不授权后续独立修改或分析（与票 01 的 YJK 一次预览确认一致）。
- **覆盖已有文件**：须另行生成覆盖操作单并单独确认（票 01 要求）。
- **未保存内容**：先由工程师选择「使用当前会话状态另存副本」或「使用已保存文件」，选择前不覆盖原文件（票 01 要求）。

### 4. 能力限制、直连绕过、部分执行与失败

- **直连绕过**：服务器闸门不依赖客户端，无有效操作单即拒绝；返回结构化错误说明取得确认的路径。直连调用方仍可自行申请操作单并回传 ID，故「禁止直连」仍是流程约束，闸门只保证执行与操作单一致、无单不执行。
- **客户端能力限制**：pi 无 elicitation、非交互无 UI、OpenCode v1 elicitation 未知——服务器闸门兜底，不依赖客户端提示；客户端提示只作可见性增强。
- **部分执行/失败**：按票 01 报告已执行内容、产物位置与未知状态；操作单记录部分完成状态；无证据不得声称已回滚。
- **只读核查**：不生成操作单；若读取需临时切换结果输出工况等选择，必须恢复原选择，恢复不了须明确报告（票 01）。

### 5. 验收

- 与票 01 五实例验收合并，按实例能力分别设用例：
  - **mutating 实例**（SAP2000 改模型副本与运行分析、Rhino 创建/调整线段、YJK 创建 YDB）：未确认拒绝、确认后执行、参数与操作单不一致时拒绝、目标变更后拒绝、部分失败报告。
  - **覆盖已有文件**：票 01 未指定覆盖实例，须另设一例（如对已另存的副本文件执行覆盖），验证覆盖须单独确认、未确认不覆盖。
  - **只读实例**（ETABS、MIDAS 读既有结果）：不生成操作单；若读取需临时切换结果输出工况等选择，恢复失败即该实例不通过（票 01）。
- **判定人**：工程师（用户）。
- **条件**：五个代表实例全部实测通过，且上述闸门用例全部通过；任一未通过不得宣称核心工作流可用。
- **审计记录**：操作单与执行记录落盘（含时间、操作内容、结果），可核；无第一方证据证明客户端提供操作者身份（票 11），不得宣称具备身份审计能力。
- 通过只证明指定实例在该环境的工作流可用，不等于结构安全、规范合格或替代工程师最终判断（票 01）。

### 范围边界

- 本票不修改票 01 已定的人工确认要求，不改变票 06 的职责划分。
- 操作单的具体字段、存储格式、文件位置与实现细节留待 SPEC 正文与实施；本票只定保障形态、责任归属、绑定语义与验收条件。
- 本票不声称任何机制已实现或已运行时验证；票 11 的未知项（OpenCode v1 elicitation、v2 elicitation 与权限规则关系、pi RPC 模式、审批台账）仍为未知。
- 部署契约（[一键部署应承诺什么行为与验收结果](08-deployment-contract.md)）负责客户端配置的具体形态；本票只要求其满足 §1 的纵深要求。
